# Project Archetypes

Choose the closest pattern and adapt it. Headings are suggestions, not required
labels.

## Research or experiment

Lead with the research question and why it matters. Then cover the method,
system, candidate contribution, quantitative results, evidence or reproduction,
and concise experimental scope or upstream attribution.

## Robotics or embodied system

Lead with the real operating context. Clarify responsibility, sensor-data-control
flow, ROS interfaces, coordinate frames or hardware boundaries, one important
system decision, demo evidence, and team attribution.

## Automation or data workflow

Lead with the operational problem and useful output. Explain data model or
architecture, provenance, recovery, idempotency or human control where relevant,
key workflows, example output, and tests or documentation.

## AI or RAG application

Lead with the demo or user experience. Explain the grounding problem, retrieval
and generation flow, implementation responsibilities, an example or evaluation,
configuration, and model/provider attribution. Do not imply model training when
the work is orchestration or integration.

## Model integration product

Lead with the end-to-end user flow. Name the upstream model, then distinguish the
candidate's product, service, UI, preprocessing, API, or deployment integration.
Show architecture and technology roles, setup or demo, and attribution. Avoid
claiming the upstream model as original work.

## Web or course prototype

Lead with the interaction or delivered outcome. Explain the request flow,
candidate-owned pages, models, endpoints, data or external integrations, notable
choices, demo, setup, and attribution. Do not add a public list of missing
production hardening.

## Portfolio or static site

Lead with the live site and a useful screenshot. Explain content organization,
navigation, custom components or styling, editable source, local preview or
deployment, and template attribution. Do not explain why portfolios matter to
recruiters.

## Library or developer tool

Lead with the outcome, installation, and first useful result. Then cover core
commands or API, design choices, tests or benchmarks, real consumers,
contribution guidance, and license.

## Variation rules

- Prefer domain-specific headings over repeated generic headings.
- Put visuals first for interaction-heavy projects and results first for
  research-heavy projects.
- Use diagrams only when they clarify a real multi-component relationship.
- Move detailed API references to dedicated documentation when available.
- A Tech Stack section must explain each technology's role, not merely list
  logos or badges.
